# 핸드오프 전 점검

Figma 화면이 **개발자가 헷갈리지 않고 만들 수 있는 상태인지** 보는 매뉴얼이에요.
코드와 Figma를 비교하는 건 `figma-reviewer`, 배포 링크를 눌러 보는 건 `flow-check`예요.

## 순서

1. **범위 받기** — 프레임 링크 하나인지, 플로우 전체(페이지·섹션)인지 물어요. 링크가 없으면 “Figma에서 프레임 선택 › 우클릭 › Copy link to selection”을 안내해요.
2. **기록 먼저** — `design-system/figma-log.md`에 이 프레임 값이 있으면 그걸 써요. 없을 때만 Figma MCP로 읽어요.
   - 플로우 전체: `get_metadata`로 프레임 목록·이름 → 화면마다 `get_design_context`
   - 읽은 값은 바로 `figma-log.md`에 날짜와 함께 적어요.
3. **기준 8개로 점검** — 아래 “기준”을 하나씩 보고 ✓ / ✗ / 확인 필요로 표시해요.
4. **보고** — 아래 “보고 형식” 그대로. 고칠 곳은 항상 Figma 레이어 이름으로 적어요.
5. **다음 제안** — ✗를 고친 뒤 다시 점검할지, 이 결과로 코드 화면을 만들지(`build-screen`) 물어요.

## 기준 (사용자가 고른 8개)

**값·정리**
1. **색이 Variables에 연결됨** — 직접 입력한 hex가 있으면 ✗ (응답에 스타일·변수 목록이 없고 hex만 있으면 직접 입력)
2. **간격·크기 4px 그리드** — 판단 기준은 `grid-check`와 같아요 (작은 요소 2px 허용, 글자 크기·줄 높이는 제외)
3. **같은 요소는 같은 스타일** — 같은 역할의 요소(예: 답 태그)가 프레임마다 굵기·색·크기가 다르면 ✗
4. **프레임 이름·번호 정리** — 같은 이름의 프레임 중복, 안이 빈 프레임, 빠진 번호(예: /7 다음 /9)가 있으면 ✗

**상태·흐름**
5. **버튼 상태 (hover·pressed·disabled)** — 판단 기준은 `state-coverage`의 요소 상태(5~8번)와 같아요. 조건이 있는 버튼(예: “모두 선택하면 제출”)에 disabled 모습이 없으면 ✗
6. **빈·긴 글·에러 상태** — 판단 기준은 `state-coverage`의 화면 상태(1~4번)와 같아요. 핸드오프 점검에서는 Figma 칸만 봐요
7. **프로토타입 연결이 분명함** — 누를 곳이 있는데 다음 화면이 없거나, 누를 곳 없이 넘어가는 화면이 있으면 확인 필요
8. **플로우의 끝 화면이 있음** — 마지막 버튼(제출·완료 등) 다음 화면이 있는지

## 보고 형식

맨 위에 판정 한 줄:
- ✗가 하나도 없으면 → **넘겨도 돼요**
- ✗가 있으면 → **고친 뒤 넘겨요 (✗ N개, 확인 필요 M개)**

| # | 기준 | 상태 | Figma 레이어 (node) | 고칠 곳 |
|---|---|---|---|---|
| 2 | 4px 그리드 | ✗ | Frame 1739334201 (7:342) 세로 간격 27 | Figma › 28로 |
| 7 | 프로토타입 연결 | 확인 필요 | 인상평가/13 (1:2352) → /14 | 디자이너에게: After delay인지, 몇 초인지 |

✓인 기준도 표에 한 줄씩 남겨요 (빠뜨린 게 아니라 통과했다는 걸 보여 주려고).

## 규칙

- **Figma를 고치지 않아요.** 보고만 하고, 고치는 건 디자이너가 해요. (`use_figma` 같은 수정 도구를 쓰지 않아요)
- **모르는 건 추측하지 않아요.** MCP로 안 보이는 것(프로토타입이 어디로 가는지, After delay 시간, 숨긴 레이어의 의도)은 ✓·✗ 대신 **확인 필요**로 적고 디자이너에게 물어요.
- 기준은 위 8개만 봐요. 새 기준을 넣고 싶으면 이 파일을 고쳐요 (`new-skill` 스킬).
